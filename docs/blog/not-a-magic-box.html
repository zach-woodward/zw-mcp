Field notes / integration

Not a magic box

Someone asked me why I didn’t just build my own MCP server. It’s not magic, they said — it’s a collection of APIs. They were right, so I built one across an entire enterprise platform. Here’s what the exercise actually taught me, most of which had nothing to do with MCP.

Zach Woodward August 2026 ~9 min

The premise was a challenge, and a fair one. Model Context Protocol had acquired a certain mystique — the thing you adopt, the thing vendors ship, the thing with a roadmap. Strip that away and you have JSON-RPC over HTTP, a manifest describing what your tools do, and a well-specified way to authenticate. That’s the whole envelope. Everything else is the API you were already going to integrate.

So I spent a few days building a server covering twelve product APIs of an enterprise agreement platform — e-signature, contract lifecycle management, workflow automation, an agreement repository, rooms, clickwraps, admin, monitoring, notary, web forms, connected fields, workspaces. Not a demo slice. The whole surface, with a deliberate escape hatch so nothing was unreachable.

It worked. Eighty-four tools, running always-on, driving real transactions. And almost every hard problem I hit was a problem I would have hit building any integration at all.

The first real decision

A thousand tools is the same as none

The obvious move is to generate one tool per endpoint. Twelve APIs is well over a thousand endpoints, and the result would be unusable: no client renders that list well, no model chooses confidently from it, and the fifteen calls a real workflow needs are buried under nine hundred that nobody will ever call.

So the tools come in two tiers. Hand-written tools cover what people actually do — find the agreements expiring this quarter, send this template to these signers, start that workflow — with descriptions aimed at a model rather than a developer, and responses trimmed to the fields that matter. Underneath, every product gets one raw_request tool taking a method, a path, and a body. Coverage is complete on day one; curation is an ergonomics layer, not a gate.

That split turned out to matter more than I expected. The curated tools are where all the judgment lives — what to return, what to hide, what to name things. The raw tool is what lets you say yes to a request at 4pm without shipping code.

Responses are a design surface. One tool returned a per-page object for every page of every document. Correct, useless, and expensive.

What actually took the time

The documentation is confidently wrong

Not maliciously. Just drifted, in the specific way that all large API documentation drifts. Six examples from one build:

  • The official spec modeled a workflow instance with one set of field names. The live API returned entirely different ones. My code, written from the spec, produced valid-looking objects with every useful field missing.
  • One API sorts and filters on different names for the same field. Filter by the nested path, sort by the flat one. Sorting by the filter name returns a 400 — which, to its credit, lists the legal alternatives.
  • The published base-path table put one product at the wrong path. Its own spec file disagreed. The spec was right.
  • The migration guide gives a documented path for folder lookup that returns 405, because that route only accepts POST. The real path is one segment deeper.
  • Two APIs in the same platform answer in snake_case; their siblings answer in camelCase. One endpoint wraps its results in data while every neighbor uses a named key.
  • A product on my build list does not exist. Six candidate endpoint shapes, all 404, zero documentation anywhere. Some names live on in slide decks long after they stop being APIs.

None of these were discoverable by reading. All of them were obvious within seconds of calling the endpoint and looking at what came back. Which is the actual lesson: verify against the live API, not the specification. The bugs that scare me aren’t the ones that throw — those announce themselves. It’s the four projection bugs that returned a well-formed object with the interesting parts quietly absent.

A distinction worth internalizing

Error messages are data

Two endpoints, two 403s, completely different meanings. One returned a bare 403 with an empty body. The other returned:

403 {"error": "Organization does not have entitlement"}

A specific error is a working endpoint. The request routed, the service recognized the organization, and it evaluated a permission. The bare 403 was the wrong host.

That difference resolved a conflict between two official sources about where a service lived. The specific error proved the request had reached the right service and been correctly refused; the empty one proved nothing. I had two plausible hosts and no way to choose — until I stopped reading and started comparing failure modes.

I got the inverse of this badly wrong earlier in the same build. An API returned consent_required, and I concluded the account lacked entitlement, wrote it up as unavailable, and moved on. It meant exactly what it said: consent had not been granted, because I had never requested it. The person I was working with told me flatly that the product was available. He was right, I was wrong, and the fix was one line in a scope list. Not authorized and not entitled are different failures, and reading one as the other cost an hour and nearly cost a whole product.

The part I didn’t see coming

MCP is also an auth spec

I built the server with a bearer token. Simple, correct, works everywhere — the CLI, the desktop app, my own code using the agent SDK. Then I tried to connect it as a hosted connector and it refused, complaining it couldn’t register with a sign-in service.

The connector UI has a URL field and two optional OAuth fields. There is no field for a header. I’d assumed one existed and gone looking for it, which was the wrong instinct; the answer was published, and I should have read it before I started guessing. The server logs told the story exactly:

POST / -> 401 GET /.well-known/oauth-protected-resource/mcp -> 404 GET /.well-known/oauth-protected-resource -> 404 GET /.well-known/oauth-authorization-server -> 404 POST /register -> 404

Four 404s. The client was doing everything right; my server had none of it.

A hosted connector doesn’t run on your machine. It connects from the vendor’s infrastructure, and it follows the MCP authorization spec: hit the endpoint, take the 401, read the WWW-Authenticate header, fetch the protected-resource metadata, discover the authorization server, register itself dynamically, then run authorization-code with PKCE. Those OAuth fields are optional precisely because dynamic registration normally fills them in.

So the server needed to be an OAuth 2.1 authorization server. Four RFCs: protected resource metadata, authorization server metadata, dynamic client registration, and resource indicators for audience binding. That sounds heavier than it is — the flow is well-specified enough that a focused implementation is a few hundred lines, and the spec explicitly allows hosting it alongside the resource server.

An hour later the same log read differently:

GET /.well-known/oauth-protected-resource -> 200 GET /.well-known/oauth-authorization-server -> 200 POST /register -> 201 POST /token -> 200

Same client, same URL, no configuration changed on its side.

The design call I’m happiest with: both paths still work. The static token authenticates local clients; OAuth serves the hosted ones. Replacing one with the other would have fixed a connector by breaking everything else I’d already wired up.

Where the boundaries landed

The interesting decisions were about exposure

Building the thing is one problem. Deciding what can reach it is a different one, and it produced the choices I thought hardest about.

The operations console — the panel that lists every tool, runs them ad hoc, and tails the logs — is a separate application. It drives the server through the same authenticated endpoint any client uses, which means it doubles as an end-to-end test: anything the console can do, a real client can do. It also means the server itself stays free of UI.

And it stays on the local network, never published. That console can send and void real agreements. The moment the server went public, the question stopped being “is this convenient” and became “what is the blast radius.” So the console refuses to bind to a public interface without a password unless you set an explicit flag saying you meant it. Fail closed, and make the override loud enough that nobody trips over it by accident.

The same reasoning kept a tempting feature out. I was asked to add a tool that toggles the public tunnel on and off. It belongs in the console, not in the tool surface — because while the tunnel is open, the tool surface is the public internet. A kill switch reachable from the thing it’s meant to kill isn’t a kill switch.

The answer to the question

So: why not just build your own?

You should, if you have a reason to. Here’s what it actually costs, honestly.

The MCP part is small. A server, a transport, a set of typed tool definitions, some resources so a model can orient itself. The protocol is well-specified and the SDK does the tedious parts. If you have integrated with an HTTP API before, you have already done the harder version of this.

The auth part is real work, and it’s the part most people will underestimate — not because OAuth is hard, but because you won’t know you need it until a hosted client refuses to connect. Budget for it if anything cloud-hosted is going to talk to your server.

Everything else — the great majority of it — is the ordinary, unglamorous work of integrating a large platform: discovering that a host is data-center-specific and must be resolved at runtime, that a documented scope your account can’t grant will fail an entire authorization request rather than being ignored, that an identifier lives in a URL tail rather than an id field. That work does not go away if you buy the connector instead. It just happens somewhere you can’t see it, and you inherit the result.

Which is the real argument for building your own. Not that it’s cheap — it isn’t particularly. It’s that when a tool returns the wrong thing, you can open the log, see the actual request, and fix it. Every one of the six documentation discrepancies above is now a comment in my source with the date I verified it and the response that proved it. None of them would have been visible to me through someone else’s black box.

MCP isn’t a magic box. It’s a thin, well-specified envelope around the integration work you were going to do anyway — and doing that work yourself is how you find out what’s actually in it.
